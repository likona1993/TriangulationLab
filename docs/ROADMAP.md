# Roadmap: от flip-алгоритма на многоугольнике к робастной триангуляции Делоне на облаке точек

## Цель

1. Привести текущий `DelaunayFlip` (триангуляция многоугольника через Ear Clipping + флипы) к структуре, пригодной для инкрементального алгоритма на облаке точек.
2. Обеспечить робастность геометрических предикатов (точная арифметика), без которой алгоритм на произвольных точках может зациклиться.
3. Перейти к триангуляции Делоне на множестве точек (supertriangle + вставка + локальные флипы).

Принцип: оптимизируем не «в лоб», а только то, что переживёт переход к облаку точек. Каждый этап заканчивается работающим, проверяемым состоянием.

---

## Принятые архитектурные решения

### Решение 1 (2026-10-22): единый индексный формат для всех трёх алгоритмов

Все алгоритмы (EarClipping, MonotoneTriangulation, DelaunayFlip) переводятся на единый внутренний формат:

```cpp
using VertexIndex = std::uint32_t;

struct Triangulation {
    std::vector<Point>                     vertices;   // V — исходные точки
    std::vector<std::array<VertexIndex, 3>>  faces;      // F — тройки индексов, CCW
    std::vector<std::array<std::int32_t, 3>> adj;       // сосед через ребро i, -1 = граница
};
```

Договорённости (по аналогии с libigl / Shewchuk's Triangle):
- внутреннее представление — **только индексы**, координаты конвертируются только на экспорте;
- все треугольники — CCW (инвариант системы);
- 0-based индексы в коде;
- `TriangulationResult<T>` меняется: вместо `std::vector<Triangle2<T>> triangles` — индексные `faces` (+ опционально `adj`), координаты через `vertices`.

Обоснование: Monotone уже работает с индексами внутри (VertexIndex, Diagonal) и теряет их только в `emitTriangle`; Ear Clipping и Delaunay Flip — нет. Единый формат устраняет конвертацию «координаты → индексы» (сейчас O(n²) через `indexOfPoint` в Delaunay Flip) и открывает путь к Этапу 2 (adj уже в структуре) и Этапу 4 (supertriangle = 3 дополнительные вершины в `vertices`).

  (`test_delaunay_flip.cpp`: `SquareTriangulation`, `ConcaveLShapeTriangulation`, `NearCollinearConvexPolygon`, `ThousandContourPointsSatisfyAllInvariants` и др.)

  (таргет `bench_delaunay`, цифры — в `docs/benchmarks.md`: 1k ≈ 0.5 с, 10k ≈ 44 с, 100k не измерялось — сложность близка к O(n²))
- [x] Тест на дубликаты точек и близко лежащие точки — зафиксировать текущее поведение.
  (`DuplicatePointsAreRejected`, `NearDuplicatePointsBehavior`: дубликаты и точки ближе ~1e-10 отклоняются как `InitialTriangulationFailed`, дальше ~1e-9 — триангулируются)

## Этап 1. Единый индексный формат (устранение O(n²) и ловушек)

Цель: все три алгоритма работают и отдают результат в индексах; убрать `indexOfPoint`, сравнение точек через `==`, конвертацию «координаты → индексы».

Замечено по коду (состояние на 2026-10-22):

- **DelaunayFlip** (`delaunay_flip.hpp`): `indexOfPoint` — линейный поиск по `m_points` с `==` по float; вызывается для каждой вершины при построении и в каждом `normalizeTriangle` при флипе. Это главный источник O(n²) и скрытых багов с дубликатами координат.
- **MonotoneTriangulation** (`monotone_triangulation.h`): внутри уже индексный (`VertexIndex = size_t`, `Diagonal = pair<VertexIndex, VertexIndex>`); индексы теряются только в `emitTriangle`, который конвертирует в `Triangle2` координатами. Переход — минимальный: хранить и отдавать `faces`.
- **EarClipping** (`ear_clipping.hpp`): работает с копией полигона и `erase` вершин из `working` — индексы «плывут». Нужна сопутствующая структура: массив исходных индексов, упорядоченный как `working` (при отрезании уха удалять из обоих параллельно). Тогда треугольник выдаётся сразу как тройка исходных индексов.

Шаги:

- [x] Ввести общий `IndexedTriangle { VertexIndex a, b, c; }` (или `std::array<uint32_t, 3>`) в `triangulation_types.h`; изменить `TriangulationResult<T>`: `faces` вместо `triangles`.
  (2026-10-27: типы `VertexIndex`/`IndexedTriangle` введены, миграция шла инкрементально через параллельные `faces` + `triangles`; legacy-поле `triangles` удалено финальным шагом Этапа 1.)
- [x] **Monotone** (сделано 2026-10-27): `emitTriangle` кладёт индексы в `faces` без конвертации (возвращает записанную CCW-грань); `triangulateMonotonePiece` принимает `faces`; классовый алиас `VertexIndex = size_t` заменён на единый `geo::VertexIndex` (uint32_t). Контракт зафиксирован тестами `MonotoneIndexedTest.*`. Debug history переведена на индексы (см. закрытый «открытый вопрос» ниже).
  ⚠️ Подводный камень миграции: `getPrevEdge` полагался на wraparound `size_t` (`(vi - 1 + n) % n`); с uint32_t это сломалось — переписано как `(vi + n - 1) % n`. При миграции DelaunayFlip проверить все `(i - 1 + n) % n`-паттерны.
- [x] **Ear Clipping** (сделано 2026-10-27, раньше Monotone): параллельный вектор исходных индексов; ухо режется одновременно из `working` и из этого вектора; результат — тройки исходных индексов в `faces`. Контракт зафиксирован тестами `EarClippingIndexedTest.*`.
- [x] **DelaunayFlip** (сделано 2026-10-27): `indexOfPoint` удалён — начальная триангуляция берёт `faces` из EarClipping напрямую; `normalizeTriangle` сведён к проверке знака cross по индексам и перестановке двух индексов; классовый алиас `VertexIndex = size_t` заменён на единый `geo::VertexIndex` (uint32_t), `oppositeVertex` возвращает `std::optional<VertexIndex>`. `triangulate` заполняет `vertices` + `faces`. Контракт зафиксирован тестами `DelaunayFlipIndexedTest.*`. Debug history переведена на индексы (см. закрытый «открытый вопрос» ниже).
- [x] Конвертация «индексы → координаты» остаётся только в одном месте: точке вызова/экспорте (визуализатор, экспорт в файл).
  (2026-10-27: legacy-поле `triangles` удалено из `TriangulationResult`; конвертация живёт в `TriangulationFacade::triangulate` для результата и в `DebugFacade` для истории; в тестах — хелпер `materializeTriangles` из `test_triangulation_utils.h`.)
- [x] Обработка дубликатов точек на входе: либо явная ошибка, либо дедупликация с документированным поведением.
  (2026-10-27: явная ошибка — новый `ErrorCode::DuplicateVertices` (категория Input); проверка `findDuplicateVertex` (сортировка + sweep, O(n log n), порог EPSILON) на входе всех трёх алгоритмов. Тесты Этапа 0 обновлены: дубликаты теперь `DuplicateVertices`, а не `InitialTriangulationFailed`. Дедупликация отложена до Этапа 4 — для полигонов она меняет топологию входа.)
- [x] Проверка: тесты Этапа 0 зелёные, результат идентичен канонизированному выводу до миграции; бенчмарк сравнить с Этапом 0 (ожидается заметное ускорение построения в DelaunayFlip).
  (2026-10-27: ctest зелёный; бенчмарк 1k ≈ 0.44 с, 10k ≈ 38.6 с — см. `docs/benchmarks.md`.)

Открытые вопросы:
- [x] Формат `DebugStep`: переведён на индексы (2026-10-27): `added_faces` (`IndexedTriangle`) + `added_diagonals` (пары `VertexIndex`) ссылаются на `vertices` запуска, которые передаются в `DebugFacade::setHistory` один раз на историю. `polygon_before` — вектор индексов; пустой = sentinel «все вершины» (флипы Delaunay, sweep-шаги monotone — не копируем O(n) индексов на шаг).
- [x] `Triangle2<T>` остаётся только как экспортный/визуальный тип: да — используется в GUI-фасаде и тестовых инвариантах, алгоритмы его больше не отдают.

## Этап 2. Локальное обновление соседства и стек флипов

Цель: убрать полный `rebuildEdgeMap` в цикле и полный перебор рёбер при поиске незаконного.

Вариант А (минимальный, без перестройки структур):
- [ ] После `flipEdge` обновлять `m_edgeMap` локально: удалить запись о старом ребре, добавить запись о новом ребре `o1–o2`; обновить записи для рёбер затронутых треугольников.
- [ ] Хранить фронт проверки: после флипа кладём в стек/очередь 4 ребра четырёхугольника + рёбра, которые соседствуют с новым; вместо `while(true) findIllegalEdge()`.
- [ ] Проверка: тот же результат, что и наивный вариант, на всех тестах Этапа 0 (побайтовое сравнение множества треугольников или канонизированного вывода).

Вариант Б (правильный, если идём к облаку точек):
- [ ] Структура «triangle + 3 соседа» (Doubly-Connected Edge List на минималках): `neighbor[i]` — индекс соседнего треугольника через сторону напротив вершины i.
- [ ] Флип обновляет 2 треугольника и 4–6 ссылок на соседство за O(1).
- [ ] Поиск незаконного ребра — обход соседства, без edge map.
- [ ] Замер: сравнить А и Б по скорости и читаемости; выбрать основной.

## Этап 3. Робастность предикатов (критично для облака точек)

Цель: исключить неверные знаки `orientation` / `inCircumcircle` на вырожденных конфигурациях — единственный реальный риск зацикливания.

- [ ] Аудит текущих предикатов в `utils/geometry_predicates.h`:
  - [ ] `orientation` — точное определение знака детерминанта.
  - [ ] `inCircumcircle` — учёт ориентации треугольника, поведение при 0 (точка на окружности).
- [ ] Ввести расширенную точность (long double / double-double) как промежуточный шаг.
- [ ] Реализовать адаптивные предикаты по Шевчуку:
  - [ ] Быстрый float-путь с оценкой погрешности.
  - [ ] Fallback на точную арифметику (расширение знаменателей) при неопределённости.
  - [ ] Минимум: корректный `orient2d` и `incircle`; `ensureCCW` поверх них.
- [ ] Инвариант алгоритма: флип разрешён только при строго положительном `inCircumcircle`; при 0 — ребро законно (детерминизм при кокруговых точках).
- [ ] Тесты на известные проблемные конфигурации: почти коллинеарные точки, 4+ точки на одной окружности, точки на далеком расстоянии (потеря значимости в double).
- [ ] Страховка верхнего уровня: лимит итераций флипов с понятным сообщением об ошибке, а не бесконечный цикл.

## Этап 4. Переход к облаку точек

Цель: триангуляция Делоне произвольного множества точек.

- [ ] Дедупликация и валидация входа (повтор Этапа 1 на новом API).
- [ ] Supertriangle: выбор размера так, чтобы все точки строго внутри; метки фиктивных вершин.
- [ ] Инкрементальная вставка:
  - [ ] Локализация точки (в какой треугольник/на какое ребро попадает) — начать с линейного поиска, при необходимости ускорить (history DAG / walk).
  - [ ] Разбиение треугольника на 3 (или двух соседних на 4 при попадании на ребро).
  - [ ] Локальные флипы стеком (механизм Этапа 2) вокруг вставленной точки.
- [ ] Удаление треугольников с вершинами supertriangle на финальном шаге.
- [ ] Convex hull получается автоматически как граничные рёбра.
- [ ] Тесты: критерий Делоне для всех рёбер, покрытие всех точек, устойчивость на кластерах/сетках/кокруговых конфигурациях.
- [ ] Бенчмарк: сравнение с Этапом 0 и оценка сложности по росту n.

## Приоритеты и риски

| Приоритет | Что | Риск при пропуске |
|---|---|---|
| 1 | Этап 3 (предикаты) | Зацикливание / неверный результат на реальных данных — блокер |
| 2 | Этап 1 (индексы) | Скрытые баги сравнения float-точек, мусорная сложность |
| 3 | Этап 2 (стек флипов) | Медленно, но корректно; можно отложить |
| 4 | Этап 4 (облако точек) | Главная цель, но только после 1–2 |
| — | Этап 0 | Нужен весь путь как страховка |

Ключевое решение: **Этапы 0–2 делаются внутри текущего класса `DelaunayFlip`**, Этап 3 — в `geometry_predicates.h`, Этап 4 — новый класс (например, `DelaunayPointSet`), переиспользующий флипы и предикаты.

## Критерии готовности к Этапу 4

- [ ] Тесты Этапа 0 зелёные на всех изменениях.
- [ ] Предикаты возвращают корректный знак на вырожденных случаях.
- [ ] Нет `indexOfPoint` в горячем пути.
- [ ] Результат триангуляции не зависит от порядка обхода edge map (детерминизм при равнозначных флипах).
